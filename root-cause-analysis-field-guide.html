Analytical Field Guide · plain English

Root Cause Analysis

Find out why it went wrong, so you can stop it happening again.

This guide is for people meeting the idea for the first time. You don’t need any background. Every new word is explained the first time it appears, and one example runs all the way through.

In short
  1. Fixing what you can see is not the same as fixing why it happened. If you only treat the surface, the problem usually comes back.
  2. Root cause analysis is a careful way to find the why. You collect evidence (facts you can check), list the possible causes, and test each one.
  3. It looks at the process, not the person. The aim is to find what let the problem happen, so you can change that.
1 · Start here

Treat the symptom, or find the cause?

Here is an everyday example. You get a headache. That is the symptom: the thing you notice. A painkiller makes the pain go away, but it doesn’t tell you why the headaches keep coming back. The reason behind them is the cause.

An everyday picture

The top row fixes what you can see. The bottom row asks why, and fixes that. Root cause analysis is the bottom row, done carefully.

Symptom

The thing you notice. The headache. The missed appointment. It shows you that something is wrong, but not why.

Root cause

The reason underneath. If you fixed it, the problem would be much less likely to come back.

Contributing cause

Something that helped the problem along, but isn’t the whole story. Often there are several, and they work together.

“Root cause” is a handy phrase, not a promise. Some problems have one clear root cause. Many have several causes that combine. Good analysis says which is which, and says so honestly.

So what is root cause analysis?

Root cause analysis (RCA for short) is a careful way of finding out why something went wrong. You gather evidence, list the possible causes, test each one, and then change what really caused the problem.

It’s about the process, not the person

Root cause analysis points at the process or system that failed, not at a person. What people did is a clue. It shows what the system made easy or hard to do.

For example, if someone skipped a step, don’t stop at “they should have been more careful”. Ask why skipping it was easy. Was the step hard to see? Was there no time? Did nothing warn them?

There is a practical reason too. If people fear blame, they stop telling you what really happened, and then you can’t find the cause.

2 · Is this the right tool?

When to use it, and when something else fits

Root cause analysis answers one question: why did this happen? Before you start, check that this is the question you are really asking.

1Fix it now

“Something is broken and people are affected.”

Fix it first. Make things safe and working again, and keep the evidence safe while you do. Find the cause afterwards.

2Find out why

“Something went wrong and we need to know why.”

This is what root cause analysis is for. The rest of this guide shows you how.

3Improve a number

“A figure is stuck below where we want it.”

Improvement work fits better. Make a small change, measure it, and keep going. We name some of these methods near the end of the guide.

4Make something new

“We need something that doesn’t exist yet.”

Design work fits better. Talk to the people who will use it, try rough versions, and learn from what they do.

5Prevent a future failure

“We want to stop a problem before it happens.”

Look ahead instead. Go through a plan step by step and ask “how could this fail?” Root cause analysis looks back at what has already happened.

Tip
You often need several of these, one after another: fix it now, find out why, then improve.
3 · The method

The steps: from problem to proven fix

Every root cause analysis has the same shape, whatever tools you use. There are six steps, and they go round in a loop.

The six steps
  1. Define the problem. Write down what went wrong, where, when and how big. Use numbers. Don’t put a cause in the sentence. “Deliveries are arriving two days late” is a problem statement. “The courier is lazy” is already a verdict.
  2. Gather evidence. Evidence means facts you can check: records, numbers, photos, and what people saw. Note where each piece came from, and whether it is a record or someone’s memory.
  3. List possible causes. Write down every cause the team can think of. Each one is a hypothesis: a possible cause the team has a reason to suspect, written down so it can be tested against the evidence.
  4. Test them and find the cause. Check each hypothesis against the evidence. Keep the ones the evidence backs and drop the ones it doesn’t. The next part of this guide shows how to tell.
  5. Fix it. Choose changes that deal with the cause you found, not just the symptom. Give every change an owner and a date.
  6. Check the fix worked. Measure again after the change. If the problem has not shrunk, go back round the loop with what you have learned.
The loop

The yellow steps, 2 to 4, are where most of the work happens. The toolkit later in this guide gives you seven tools that help with them.

4 · Testing your ideas

How to tell if a cause is real

A cause that sounds right is not always a cause that is right. For every possible cause, ask these six questions.

Question 1

Did it happen before the problem?

A cause has to come first. If the thing you suspect only appeared after the problem started, it can’t be the cause.

Question 2

How exactly would it cause this?

Tell the story step by step: this happened, so that happened, so the problem followed. If you can’t explain how it actually caused it, you may only have a coincidence.

Question 3

Does it show up where things went wrong, but not where they went right?

Compare cases that went badly with cases that went well. A real cause is usually present in the first group and missing from the second.

Question 4

What else could explain it?

Write down the other explanations and check those too. Don’t quietly drop the awkward ones.

Question 5

If it hadn’t happened, would things have turned out differently?

That is the test of whether it really matters. Be honest about what you are assuming when you answer.

Question 6

How sure are we?

Give every conclusion a plain label, and say why. Base the label on the quality of the evidence, not on how senior the person is who said it.

Here are three labels you can use.

Your brain takes shortcuts

Everyone’s brain jumps to the first explanation that feels right, then notices mostly the evidence that agrees with it. This is called bias. It happens to everybody, including experts.

Two habits help. Ask “what evidence would prove this wrong?” and go looking for it first. And ask someone outside the team to challenge your list.

When to stop digging
  • The important causes are backed by evidence.
  • You have checked the other explanations.
  • You can measure whether a fix works.

Stop too soon and you fix the wrong thing. Never stop and nothing gets fixed.

5 · One example, all the way through

Meet the example

Every tool in this guide is shown on the same case. It is made up. It is written in the style of a National Health Service (NHS) outpatient clinic, where people come in for an appointment and go home the same day. It does not describe any real hospital or patient. When a detail is invented just to make a picture work, we mark it “illustrative”, which means “made up as an example”.

Our example (made up)

A hospital changed to a new booking system. Afterwards, more patients stopped turning up for their appointments.

The team’s question: why did missed appointments go up after the booking system changed, and what should we change?

The team wrote down five possible causes. Each one is a hypothesis:

  • Hypothesis 1: reminders weakened when patient records were copied to the new system.
  • Hypothesis 2: appointments were booked further ahead, so the wait got longer.
  • Hypothesis 3: there were fewer workable ways to rebook.
  • Hypothesis 4: a different mix of clinics and patients was being booked.
  • Hypothesis 5: the rise came from counting differently: a changed meaning of “missed”, or a different total to count out of.

The seven tools below take these five apart. The full case, with every finding, comes at the end of the guide.

Tool 1 of 7 · put events in order

Timeline

A list of what happened, in the order it happened, with the time and where each fact came from.

1What it’s for

It shows what came first. A cause has to come before its effect, so the order matters. It also shows the gaps: the things you don’t know yet.

Use it when you need to understand what happened before you decide why.

2How to do it
  1. List every event you know about, with its date and time.
  2. Next to each one, write where it came from: a record, a computer log (an automatic list of what a system did), or someone’s memory.
  3. Put the events in order, using one clock for all of them.
  4. Mark the gaps, and anything two sources disagree about. Don’t fill a gap with a neat story.
  5. Look at what changed just before the problem started.
3Shown on our example

The order is clear: the system went live, records were copied across that night, and reminders began failing two days later. Staff remember reminders being fine before that, but memory is not a record. It stays apart from the line until someone checks it. The last two events have nothing between them, so the gap is shown rather than filled in. The staff memory is illustrative.

4Watch out for
  • A neat story can hide a gap. If you don’t know, say so.
  • Someone’s memory is a clue, not a fact. Keep it separate until a record backs it.
  • Check the clocks. Two systems can disagree about the time.
  • A long list of times is not a timeline until you can see what led to what.
Tip
Use one mark for “a record” and another for “someone’s memory”. It stops memory being treated as fact.
Tool 2 of 7 · dig down to what you can fix

5 Whys

Ask “why?” about a problem, then ask “why?” about the answer, and keep going. Five is a rule of thumb, not a rule.

1What it’s for

It takes you from what you can see to something you can change. Each answer becomes the next question. You stop when you reach something your team can actually fix.

Use it when the cause may be a chain of events, with one thing leading to the next.

2How to do it
  1. Write the problem as a plain statement.
  2. Ask “why did this happen?” Answer from evidence, not from opinion.
  3. Take that answer and ask “why?” again. Repeat until you reach something your team can change.
  4. If an answer has two causes working together, split the path in two and follow both.
  5. Read the path backwards, saying “so” between the steps. If a “so” sounds wrong, a step is missing.
3Shown on our example

The path starts with one patient who got no reminder and ends at two causes the team can change: a check list that never covered this setting, and no rule to review what else depends on a setting when data is moved. The fifth “why” has two answers at once, so the path splits in two.

4Watch out for
  • Don’t stop at a person. “Staff didn’t check” is a clue. Ask what made checking hard.
  • Answer each “why” from evidence. If you can’t, mark it as not checked yet.
  • Real problems often branch. One chain can hide a second one.
  • Five is only a guide. Stop when you reach something you can change.
Tip
Read your path backwards with “so” between the steps: “The check list never covered the setting, so the setting wasn’t carried over, so the number was marked not contactable, so no reminder was sent.”
Tool 3 of 7 · list every possible cause

Fishbone diagram

Also called an Ishikawa diagram, after Kaoru Ishikawa, the Japanese quality expert who made it popular.

1What it’s for

It helps a team write down every possible cause of a problem before choosing one. That stops you fixing the first thing someone thinks of.

Use it when a problem could have several causes and people disagree about which one matters.

2How to do it
  1. Write the problem at the head of the fish, with numbers if you have them.
  2. Draw the spine. Add a bone for each heading that fits your problem, such as people, process, technology or measurement.
  3. On each bone, write the causes the team suspects. Each one is a hypothesis: a possible cause you have a reason to suspect, written down so it can be tested.
  4. Check each one against the evidence. Mark it backed, ruled out, or not checked yet.
  5. Take the ones that survive forward, into a 5 Whys or a fix.
3Shown on our example
Highlighted: backed by evidenceCrossed out: evidence against it? : not checked yet

Hypotheses 1 to 5 are the five listed in our example (section 5), with the full findings at the end. Three held up. Two were ruled out. Waiting time did not cause the problem on its own, but it made the reminder problem worse.

4Watch out for
  • An idea on the diagram is not a cause until the evidence backs it.
  • Be specific. “Technology” is a heading, not a cause.
  • Causes can work together. One can make another worse.
  • Say which ideas you have not checked yet.
Tip
Write each cause as something that happened (“reminders stopped reaching patients”), not as a single word (“technology”).
Tool 4 of 7 · compare before and after

Change analysis

Put what was true before next to what is true after, and see what changed.

1What it’s for

It finds everything that is different between a time when things went well and a time when they went badly. Then you test which of those differences could really explain the problem.

Use it when you know roughly when the problem began, so you have a clear “before” and “after”.

2How to do it
  1. Pick the two things to compare: before and after the problem started, or a team that did well and one that didn’t.
  2. List everything that is different. Include small things: rules, tools, settings, numbers, people.
  3. For each difference, ask: does it explain the problem? Check the timing, the size, and how it would cause it.
  4. Cross out the changes that can’t explain it. Keep the rest as possible causes.
  5. Remember that changes happening together are not all causes.

  • Not every change is a cause. Test each one.
  • Small changes are easy to miss. Ask the people who do the work what feels different now.
  • Compare like with like: the same clinics, the same kinds of appointment.
  • Check the timing. A change that came after the rise can’t have caused it.
Tip
Ask the people who do the work what feels different now. They often spot changes that no record shows.
Tool 5 of 7 · find the safeguards that failed

Barrier analysis

A barrier is a safeguard: anything meant to stop a problem, spot it, or limit the damage.

1What it’s for

It asks which safeguards should have stopped the harm, and why each one didn’t. Picture slices of Swiss cheese. Each slice is a safeguard, and each has holes. Harm gets through when the holes line up.

Use it when something went wrong even though checks were in place.

2How to do it
  1. Write down the harm you want to stop.
  2. List every safeguard that should have stopped it, spotted it, or limited it: checks, alerts, rules, back-up routes.
  3. For each one, ask: did it work as intended? If not, where was the hole?
  4. For each hole, find out why it was there, using evidence.
  5. Trace the path: one arrow through all the holes shows how the harm got through.
3Shown on our example
Each slice: a safeguardEach hole: where it failedRed arrow: the path the harm took

Four safeguards could each have stopped the missed appointments. The check at the copying stage missed the setting. The reminder system did not spot the wrongly marked numbers. Failed messages were not reliably followed up. The online rebooking route was gone. Each had a hole, and the holes lined up.

4Watch out for
  • Don’t list “staff training” as a safeguard unless the system makes the right action easy.
  • A safeguard can exist on paper and not work in practice. Check what really happened.
  • Safeguards that rely on someone remembering are the weakest.
  • Look for safeguards that were missing, not only ones that failed.
Tip
Ask “which of our safeguards depends on someone remembering?” Those are usually the weakest slices.
Tool 6 of 7 · find where most of the problem is

Pareto chart

Named after Vilfredo Pareto, an Italian economist. The idea: a few causes often account for most of the trouble.

1What it’s for

It shows where most of a problem sits, so you start looking there instead of everywhere. You split the total into groups, count each group, and draw the bars from biggest to smallest.

Use it when you have a big total and need to decide where to look first.

2How to do it
  1. Choose what you are counting. Here it is the 460 extra missed appointments.
  2. Choose how to split it into groups: clinics, days of the week, types of fault.
  3. Count each group.
  4. Sort the groups from biggest to smallest, and draw the bars in that order.
  5. See how much the first one or two bars cover. Start your investigation there.
3Shown on our example
Yellow bars: the biggest twoIllustrative: the split by clinic is made up

Clinics A and B together account for 276 of the 460 extra missed appointments. That is 60%. The bars fall from left to right because we sorted them biggest first, on purpose. The tall bars on the left tell you where to look first. The 460 comes from the case. How it divides between clinics is illustrative.

4Watch out for
  • A big bar tells you where the problem is, not why. It is not a cause.
  • A small group can still matter. A few serious cases may be worth more attention than many minor ones.
  • Choose the groups carefully. Different splits can tell different stories.
  • Sort first, then look. The order the groups arrive in shouldn’t decide where you look.
Tip
Try more than one split: by clinic, by week, by type of appointment. The one where a few bars stand tall is usually the useful one.
Tool 7 of 7 · see how causes fit together

Fault tree

A fault tree starts with the bad outcome at the top and branches down to everything that had to happen for it to occur. The branching points are called gates.

1What it’s for

It shows how causes combine. Some outcomes need several things to go wrong together. Others can happen in several different ways. The tree makes that visible.

Use it when more than one cause is involved and you want to see how they fit together.

2How to do it
  1. Write the bad outcome in a box at the top.
  2. Ask: what would have to be true for this to happen? Write the answers underneath.
  3. Decide how they combine. Do ALL of them have to happen, or is ANY ONE enough? Mark it with a gate.
  4. Keep splitting each box the same way until you reach causes you can check or change.
  5. Check each box against the evidence. Mark anything with no evidence as not checked.
3Shown on our example
Yellow gate: ALL of these must happenGreen gate: ANY ONE is enough

Read it from the top down. A patient can miss an appointment in either of two ways, and ANY ONE is enough: they forgot, or they knew they couldn’t come but couldn’t move it. Someone who forgot never tries to rebook, so these are separate routes, not two things that both had to happen. Forgetting has two routes of its own. The ALL gate in the middle shows that a failed message only costs an appointment if nobody follows it up. That is why the list of failed messages in the barrier analysis counts as a safeguard. This tree is illustrative: one way the case findings could fit together, not a new finding.

4Watch out for
  • A gate must be honest. Don’t write “ANY ONE” when really it takes all of them.
  • Keep going until you reach causes you can check or change.
  • A box with no evidence behind it is a hypothesis, not a finding.
  • One tree shows one outcome. Draw a separate tree for each outcome.
Tip
If a box has “ANY ONE of these” under it, fixing one cause isn’t enough: the others can still do the damage. Where you see “ALL of these happened”, breaking just one link is enough.

8 · Making the fix last

Fixes that actually work

Finding the cause is only half the job. Some fixes are much stronger than others, and the weakest ones are the easiest to reach for.

Three levels of fix

Memos, warnings and retraining depend on people remembering, so they wear off. Fixes that make the right action easier last longer. The strongest ones change the system, so the problem can’t happen the same way again. Use a weak fix only as a stopgap, or alongside a stronger one. The first example is illustrative. The other two are among the team’s actions in the full case.

Strong isn’t always safe

A strict new rule can block a sensible exception. An automatic step can hide new problems. Try the fix out with the people who will use it, keep a way round, and watch for new trouble.

Five questions for any fix
  • What exactly will change, where, and for whom?
  • Which cause does it deal with?
  • Who owns it, and by when?
  • How will we know it was done, and that it worked?
  • What new problem could it cause?
9 · Beyond the seven tools

Going further

Root cause analysis is one family of tools. This part names its neighbours, so you know what to look for next. Knowing the names is not the same as investigating well. A neat diagram can’t replace good records, careful questions and talking to the people who do the work.

Looking back

For when something has already gone wrong and the causes are tangled. Each one looks at a different slice of the picture.

Work-system map

SEIPS: Systems Engineering Initiative for Patient Safety

Looks at the people, their tasks, their tools, the organisation and the surroundings together, and at how they affect each other. The value is in those links, not in sorting facts into boxes.

Use it when the problem comes from how several parts of the job fit together, not from one broken part.

Everyday-variation map

FRAM: Functional Resonance Analysis Method

Maps each job in a process and how it normally varies, for example in timing or quality. Then it asks how ordinary ups and downs can add up to a bad day, even though nothing broke.

Use it when a process usually works because people adapt, but now and then it fails and no single thing broke.

Levels map

AcciMap: short for “accident map”

Lays out who did what at each level, from national rules down to the people affected, and shows how decisions higher up shaped what happened lower down. Our example is drawn this way. Decisions flow down, and their effects show up at the bottom.

Use it when local actions were shaped by decisions, budgets or rules made higher up.

Control review

CAST: Causal Analysis based on System Theory

After a serious loss, asks why the rules, checks and feedback at every level did not stop it. It looks at what each level was meant to control, and what it was never told.

Use it when a serious incident involved people, software and management decisions together. It needs skilled help and a clear edge around the system you are studying.

Process mining

Uses the time-stamped records that computer systems keep automatically, from thousands of cases, to draw the routes work really took and where it got stuck or went off course. A pattern still needs a person to explain it.

Use it when the same process runs again and again, and you have the records.

Working out what really made the difference

Causal inference

Methods for telling whether something really changed an outcome, or just happened to show up alongside it. The main trap is a confounder: something that drives both the thing you suspect and the outcome.

Use it when you need to know whether a change really made a difference, and you have enough data to compare.

Everyday example, not from our case. Ice cream sales and sunburn both rise in summer. Ice cream doesn’t cause sunburn. Hot, sunny weather drives both. The weather is the confounder.

AI-assisted investigation

AI: artificial intelligence

Computer programs can summarise records, group similar incidents, spot odd patterns and suggest possible causes. They narrow the search. They don’t give you the answer, and fluent writing can make a wrong story sound right.

Use it when you have more records than people can read. Keep a person in charge, keep track of where each piece of evidence came from, and check every suggestion against the evidence.

Looking forward

Root cause analysis looks back. These tools look ahead, to find weak spots before anything goes wrong.

Failure check, step by step

FMEA: Failure Modes and Effects Analysis

List each step of a process, how it could fail and what would happen. Score how bad and how likely each failure is, then fix the worst first.

Use it when you are designing or changing something and want to find the weak spots before launch.

Guide-word review

HAZOP: Hazard and Operability study

A team walks through a design step by step, using guide words such as “no”, “more”, “less” and “too late”. For each step it asks: what if this drifts from the plan?

Use it when you are checking a design before it goes live, especially where things flow through it, such as materials, data or patients.

Control-gaps review

STPA: System-Theoretic Process Analysis

Looks at who or what gives instructions in a system, and what feedback comes back. Then it asks how an instruction could be missing, wrong or badly timed, and lead to harm.

Use it when you are designing something where software and people work together and harm would be serious.

Bow-tie picture

Draws the bad event as the knot of a bow tie. Threats fan in from the left. Consequences fan out to the right. Safeguards sit across both sides, here shown on our example.

Use it when you want to see on one page what stands between a threat and a harm.

After the diagnosis

Once you know the cause, these help you try a fix, check it, and make it last.

Try it small, then decide

PDSA: Plan, Do, Study, Act

Plan a small change. Try it on a small scale. Study what happened. Then act: keep it, adjust it or drop it, and go round again.

Use it when you are not sure a fix will work and want to test it cheaply first.

One-page problem report

A3 is a paper size. The method is named after the sheet it is written on.

Fits the problem, the causes, the fix and the follow-up on a single sheet, so the team and its managers share one short story.

Use it when you want everyone to agree on what the problem is, what is being done and who is doing it.

Cut out waste

Lean

A way of running work that removes waste, meaning steps that add nothing for the person being served, and keeps improving in small steps.

Use it when the trouble is slow, clumsy work more than one single failure.

Five stages for a stuck number

DMAIC: Define, Measure, Analyse, Improve, Control

Comes from Six Sigma, a quality method used in industry. You define the problem, measure it, analyse the causes, improve the process, then control it so the gain lasts.

Use it when a measured result, such as waiting time, is stuck, and you need to improve it and keep it there.

What they found

Each finding carries a plain label. Strong: the records, the timing and how it caused the problem all line up. Supported: several sources agree and nothing contradicts it. Weakened: the evidence made the idea less likely, though not impossible.

Hypothesis 1Strong

Reminders were damaged when records were copied

About 70% of the 460 extra misses (roughly 320) had no successful reminder attempt. That figure is illustrative. Some valid contact records no longer met the new rule for sending reminders. The send records gave the timing.

See Timeline, 5 Whys and Barrier analysis.

Hypothesis 2Supported

Long waits made it worse

Appointments booked six or more weeks ahead always had higher miss rates, and their share rose after the change. This made things worse. It did not cause every miss.

See Change analysis.

Hypothesis 3Supported

Moving an appointment got harder

The self-service rebooking route disappeared and abandoned calls rose. Walk-throughs and patient accounts showed that some people tried and could not move their appointment.

See Change analysis and Fault tree.

Hypotheses 4 and 5Weakened

Two rival explanations became less likely

The counting rule did not change. The mix of clinics was broadly stable, though the extra misses were concentrated in two clinics. That makes “different mix” and “counted differently” less likely. It does not rule them out, and the report should say what is still uncertain.

See Change analysis and Pareto chart.

What they decided to do

The actions
  1. Repair how contact settings are copied across, and check before going live that reminders can be sent.
  2. Set up a visible list of failed reminders, with an owner and rules for what to do.
  3. Bring back an easy way to rebook, online and by phone.
  4. Shorten long waits where clinic capacity and medical priority allow.
  5. Try the changes with patients and booking staff before a full roll-out.
How they will check it worked
  • Main measure: the missed-appointment rate, for each clinic and each patient group.
  • Steps along the way: reminders sent and delivered, and rebookings completed.
  • Things that must not get worse (these are called guardrails): waiting time, abandoned calls, staff workload, and fair access for every patient group.
  • When: review after eight weeks, with enough appointments for a steady comparison. Check that the changes were made, and separately that they worked.
  • Reopen the case if the total improves but one group gets worse.

This counts as root cause analysis, and not just a story, because the team started with five possible causes, tested each one against evidence, said how sure it was, and set out how it would check the fix.

11 · Before you call it finished

A checklist to keep

Use it to brief the work at the start, and to check it at the end.

Ten questions
  • Problem. What went wrong, where, when and how big? Use numbers. Leave the cause out of the sentence.
  • Quick fix. Is it safe now? Is the evidence being kept?
  • Scope. What is our question? Who is on the team, including people who do the work?
  • Facts. Is there a timeline with the source of each fact, and a note of what is unknown or disputed?
  • Possible causes. Is each one written as a hypothesis, with the evidence that would test it?
  • Tests. Is there evidence for and against each one? Have we checked other explanations and said how sure we are?
  • Learning. What went well, and what limited the harm?
  • Actions. Does each one deal with a cause we backed? Does it have an owner, a date and a way to show it was done?
  • Checking. Which measure shows it worked? What must not get worse? When do we look, and who reviews?
  • Reopen. What result would send us back to investigate again?

The investigation is finished when the fix has been tested against real life, not when the report is signed.
